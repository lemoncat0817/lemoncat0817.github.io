## 這是什麼

MAJI Tea POS 是一套給手搖飲料店用的點餐系統。它不只是「能點餐」而已 —— 從店員登入、選飲料改甜度冰塊、套用折扣、結帳，到店長查看歷史訂單、調整後台設定、看營運數據圖表，是一條完整的營運動線。

這是我目前做過**規模最大、模組最多**的專案，也是最接近真實商業需求的一個。

## 問題背景

手搖飲料店的點餐有幾個和一般電商很不一樣的地方：

1. **速度就是一切**。尖峰時段店員一分鐘要處理好幾張單，任何多餘的點擊都是成本。
2. **選項組合爆炸**。同一杯飲料有容量、甜度、冰塊、加料的排列組合，UI 不能讓店員迷路。
3. **店員和店長要看的東西完全不同**。店員只需要點餐畫面；店長要的是報表和設定。

所以這個專案真正的挑戰不是「做出功能」，而是**讓兩種角色各自看到剛好夠用的介面**。

## 我的做法

我把系統切成七個模組：

| 模組 | 解決的問題 |
| --- | --- |
| 登入頁面 | 辨識身分，決定後續看到什麼 |
| 點餐功能 | 主要工作區，追求最少點擊完成一張單 |
| 折扣系統 | 處理促銷與會員優惠 |
| 歷史訂單 | 查單、對帳、處理客訴 |
| 後台設定 | 品項、價格、選項的維護 |
| 數據分析 | 用 ECharts 把營業狀況視覺化 |
| 權限管理 | 控制誰能看到哪些模組 |

版面用 **Element Plus** 打底，因為它的表格、表單、對話框元件成熟且鍵盤支援完整 —— POS 這種高頻輸入的場景，鍵盤操作比滑鼠重要。細節樣式再用 **Tailwind CSS** 和 **Sass** 補上。

## 技術決策與取捨

### 為什麼用 Pinia 而不是把狀態塞在元件裡

點餐車的狀態要同時被點餐區、訂單明細、結帳彈窗讀取。如果用 props 一層層傳，加一個功能就要改三個檔案。

我用 **Pinia** 把購物車、使用者身分、後台設定拆成三個獨立的 store。搭配 `pinia-plugin-persistedstate` 把狀態寫進 localStorage —— 這解決了一個很實際的問題：**店員手滑重新整理頁面，還沒結帳的訂單不會消失**。

### 為什麼選 Element Plus 而不是自己刻

我評估過自己刻元件。但 POS 系統的價值在業務邏輯，不在重造一個表格元件。Element Plus 讓我把時間花在「折扣怎麼算」而不是「下拉選單怎麼做」。

代價是 bundle 較大、客製化樣式時要跟它的 CSS 權重打架。以這個專案的性質（店內裝置、非公開網頁、不吃 SEO）來說，這個交換是划算的。

### 權限管理用路由守衛而不是隱藏按鈕

一開始我只是把店長專用的按鈕 `v-if` 掉。後來意識到這只是「看不到」，不是「不能進」—— 直接改網址還是進得去。

改成在 **Vue Router** 的 `beforeEach` 做守衛，依角色決定能不能進該路由。這是我在這個專案學到最重要的一課：**前端的權限控制是體驗，不是安全**。真正的把關必須在後端；前端做的是「不要讓使用者走到死路」。
