## 這是什麼

氣象知多少的第二個版本。第一版是查詢型 SPA——輸入城市、看預報。這一版把定位改成「颱風天、地震後真的會打開來看」的資訊平台：雷達回波動畫、颱風路徑與不確定性錐、地震震度分布、全台警特報彙整全部長在同一個網站裡，而且部署在 Cloudflare 的邊緣網路上。

## 問題背景

上一版留下兩個明確的技術債：API 金鑰整包在前端 bundle 裡看得到，以及沒有任何快取、每次切城市都重新打一次中央氣象署的 API。這兩個問題只有一個解法——需要一個真正會執行程式碼的伺服器層，純前端解決不了。

同時，中央氣象署（CWA）的開放資料本身也是老問題：預報、觀測、颱風、地震四種資料集的欄位命名、巢狀深度、大小寫慣例互不一致，各自長得完全不一樣。

## 我的做法

換成 Nuxt 4，讓同一個專案同時擁有前端頁面和伺服器 API 路由（Nitro），部署到 Cloudflare Workers：

- **金鑰只活在伺服器端。** CWA 金鑰透過 `useRuntimeConfig()` 在請求當下讀取，不會進到前端 bundle，也不會出現在任何 API 回應裡。
- **反腐層統一資料形狀。** `server/utils/normalize/**` 把預報、觀測、颱風、地震四種完全不同的 CWA 回應，轉成 `shared/types` 定義好的領域模型。前端元件只認得自己的型別，不需要知道 CWA 原始 JSON 長什麼樣。
- **依資料時效分層快取。** 變動快的雷達回波快取 5 分鐘，預報快取 30 分鐘，幾乎不變的氣候常態快取 6 小時——每支 API 用 `defineCachedEventHandler` 各自設定 TTL，在 Workers 上用 KV 承載，同一份資料不會被重複打上游好幾次。
- **地圖與圖表各司其職。** MapLibre GL 負責雷達回波動畫、測站觀測與 368 鄉鎮溫度的 choropleth；ECharts 負責 24 小時 meteogram 與颱風強度時序這類時間序列圖。

## 技術決策與取捨

### 為什麼從 Vue SPA 換成 Nuxt

純前端架構解決不了「金鑰要藏起來」這個根本問題——藏金鑰需要一個會執行程式碼的伺服器，不只是靜態檔案。Nuxt 的 Nitro 讓我不用額外維護一個獨立的後端專案，同一個 repo、同一次部署，就同時有了頁面和 API。

### 為什麼部署在 Cloudflare Workers 而不是傳統 serverless

氣象資料的特性是「大量讀取、少量即時性要求」——多數使用者查的是自己所在城市，快取命中率天生就高。Cloudflare 的邊緣網路讓 API 回應從離使用者最近的節點送出，加上 KV 作為跨節點共享的快取層，這個組合對讀取密集的場景特別合適。

### 反腐層值得的成本

四種 CWA 資料集各自要寫一支正規化函式，短期看是多寫了程式碼。但這個成本是一次性的，換來的是前端元件完全不用碰巢狀 JSON、氣象署改欄位名稱時只要修一個檔案——這是延續上一版學到的教訓，這次做得更徹底。

## 遇到的坑

**雷達回波動畫要在伺服器端做滾動視窗。** CWA 的雷達圖資源是逐張的靜態圖層，直接把所有歷史影格丟給前端，載入時間會隨時間累積。改成伺服器只回傳最近一段時間的影格清單，前端不需要自己判斷哪些該丟棄。

**颱風不確定性錐的機率是內插算出來的，不是 CWA 直接提供。** 氣象署公開的是逐報路徑點，70% 機率圓半徑要依預報時效內插——這段是純前端算出來的視覺化，不是照搬 API 回傳值。

## 成果

CI 在推送到 `master` 時跑型別檢查、Lint、測試三道關卡，全數通過才建置並部署到 Cloudflare Workers。線上版本可以直接查全台任一縣市的天氣、地圖與颱風動態。

## 如果重做我會怎麼改

1. **雷達動畫加上時間軸拖曳。** 目前只能看最新影格序列自動播放，讓使用者能拖到任一時間點會更實用。
2. **警特報加上推播訂閱。** 現在警特報只在打開網站時看得到，針對特定縣市的訂閱制推播通知，會讓這個功能真正派上用場。
3. **把地震資訊延伸到歷史查詢。** 目前只顯示近期地震，加上依規模／地區篩選的歷史查詢，會讓這個版位更完整。
