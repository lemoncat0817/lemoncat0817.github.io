## 這是什麼

「氣象知多少」串接中央氣象署（CWA）的開放資料，把原始的氣象 API 回應整理成一般人看得懂的介面：現在幾度、等等會不會下雨、未來幾天如何、有沒有發布警報。

這是我**第一個用 TypeScript 寫的專案**，也是第一個大量處理外部 API 資料的專案。

## 問題背景

政府開放資料的價值很高，但格式是給機器看的，不是給人看的。

中央氣象署的 API 回傳的是深層巢狀結構 —— 要拿到「台北市今天的最高溫」，得穿過好幾層 `location → weatherElement → time → parameter` 才找得到，而且不同的 API 端點（預報、觀測、警報）結構還不一樣。

所以這個專案的核心工作其實是**資料轉換**：把三種不同形狀的 API 回應，正規化成前端好用的統一格式。

## 我的做法

我把應用切成幾個功能面：

- **即時天氣** —— 目前的溫度、體感、濕度、天氣描述
- **多日預報** —— 未來幾天的趨勢
- **城市搜尋** —— 切換不同縣市
- **氣象觀測資料** —— 實際測站的觀測值
- **氣象警報** —— 有發布時主動顯示
- **深色模式** —— 尊重系統偏好

資料流是：`Axios` 取得 API 回應 → 轉換層正規化 → `Pinia` store 存放 → 元件只讀取整理好的資料。元件完全不需要知道 CWA 的原始格式長什麼樣。

## 技術決策與取捨

### 為什麼從這個專案開始用 TypeScript

上一個專案（MAJI POS）是純 JavaScript。當時訂單物件在模組之間傳來傳去，我常常要回頭翻程式碼確認「這個物件到底有沒有這個欄位」。

而處理外部 API 的情境把這個痛點放大了十倍 —— API 回傳的巢狀結構深、欄位名稱不直覺，而且**你無法控制它**。我為 CWA 的回應定義了 interface，這樣：

1. 拆解巢狀結構時，編輯器會提示下一層有什麼欄位
2. 氣象署改格式時，型別檢查會直接報錯，而不是等到畫面上出現 `undefined`

這是我第一次真正體會到型別不是「額外的工作」，而是**把 runtime 的錯誤提前到編譯期**。

### 把 API 轉換層獨立出來

我沒有在元件裡直接呼叫 API 然後就地拆解資料。所有 CWA 的資料都先經過一層轉換函式，輸出乾淨的物件。

好處是：氣象署的 API 格式如果改了，我只要改轉換層，元件一行都不用動。這是我從 POS 專案學到的教訓的延伸 —— **把會變動的東西關在一個地方**。

### 深色模式跟隨系統偏好

用 `prefers-color-scheme` 讀取使用者的系統設定作為預設值，而不是強制某一種。查天氣這個行為很常發生在早晨或睡前，深色模式在這些情境下是實際需求，不是裝飾。

## 遇到的坑

**時間格式不統一。** CWA 不同端點回傳的時間字串格式不一致，而且 Safari 對 `new Date()` 能解析的字串比 Chrome 嚴格 —— 在 Chrome 上正常的日期，到 iPhone 上變成 `Invalid Date`。這是我第一次踩到跨瀏覽器的日期解析差異，最後統一在轉換層處理成標準格式。

**API 金鑰直接放在前端。** 這是純前端專案的先天限制 —— 打包後金鑰一定看得到。我當時的處理是使用有申請額度限制的授權碼。正確的做法應該是加一層後端代理，這點我在下面的檢討有寫。

## 成果

七項功能全部完成並上線，可以直接在 Demo 查詢任一縣市的天氣。

## 如果重做我會怎麼改

1. **加一層後端代理來藏 API 金鑰。** 這是目前架構最明確的弱點。用一個極簡的 serverless function 轉發請求就能解決。
2. **加上快取。** 氣象資料不會每秒變，但目前每次切換城市都重新請求。以 CWA 的資料更新頻率來說，快取幾分鐘完全合理，能大幅減少請求數。
3. **失敗狀態要做得更好。** 目前 API 掛掉時的處理偏陽春。使用者需要知道「是網路問題還是氣象署掛了」，以及「還能不能看到剛才的資料」。
