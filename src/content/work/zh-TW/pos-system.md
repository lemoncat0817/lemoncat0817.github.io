## 這是什麼

pos-system 是一套給餐飲與飲料店用的多租戶 POS 系統。從店員登入、點餐、套用會員折扣、結帳，到店長查歷史訂單、管後台設定、看營業數據，是一條完整的營運動線。前端和後端都是我從零寫起的。

這是我目前做過**規模最大、模組最多**的專案：正式後端、多租戶資料隔離、跨裝置離線同步全部到位。

## 問題背景

餐飲業 POS 有幾個和一般後台系統很不一樣的現實：

1. **網路不可靠是常態**。門市 Wi-Fi 斷線時收銀不能停擺，訂單得先收下來再說。
2. **一套系統要服務多家店**，資料庫共用同一份，但租戶之間的資料必須完全隔離，一條漏掉租戶過濾的查詢就是資安事故。
3. **同一台裝置上有三種不同的身分**：裝置本身、當班操作員、後台擁有者，各自的信任層級不同，不能用同一把 session 打天下。

所以這個專案的重點放在三件事：**斷網時收銀照常運作、多租戶資料不會互相外洩、權限由後端實際把關**。

## 我的做法

我把系統拆成七個模組：

| 模組 | 解決的問題 |
| --- | --- |
| 點餐收銀 | 主要工作區，離線也能繼續收單，追求最少點擊完成一張單 |
| 桌況管理 | 內用桌位即時狀態卡片，掌握入座時間與備註 |
| 會員行銷 | 會員等級門檻、點數累積、折扣券 |
| 訂單中心 | 多維度篩選、發票載具記錄、退款作廢與稽核追蹤 |
| 權限與班別 | RBAC 角色權限、OAuth 後台登入、收班現金帳差計算 |
| 數據分析 | 用 ECharts 呈現營業額趨勢與熱銷排行 |
| 離線同步引擎 | Dexie 佇列＋指數退避同步，斷網也能正常收單 |

前端是 Vue 3 + TypeScript strict 寫成的 PWA，離線優先；後端是 Hono 跑在 Cloudflare Workers 上，資料存在 D1，用 Drizzle ORM 操作。前後端共用的業務邏輯與 API 契約，抽成兩個獨立套件，不各自維護一份。

## 技術決策與取捨

### 為什麼把領域邏輯與 API 契約拆成獨立套件

前後端如果各自重寫一份金額計算、折扣規則、API 型別，兩邊定義兜不起來就是一次線上事故。我把純 TypeScript 的領域邏輯（金額計算、折扣、退款、班別）和 Zod API 契約各自抽成獨立套件，前後端 import 同一份程式碼，兩邊的定義只要對不上，型別檢查就會直接報錯。ESLint 的依賴邊界規則會擋下這兩個套件誤依賴 Vue／UI 框架，逼它們維持純邏輯。

### 為什麼是單一資料庫多租戶，而不是每租戶一個資料庫

Database-per-tenant 在隔離上更讓人放心，但 Cloudflare D1 的資料庫數量與冷啟動成本會隨租戶數線性增加，維運複雜度很快就會失控。我選單一 D1 多租戶，換來的代價是**每一條查詢都要自己記得帶 tenantId 過濾**。為了不靠人腦記憶，我把它包成共用的查詢 helper，寫查詢時就很難漏掉租戶過濾，不必等到 code review 才發現。

### 為什麼是三種獨立憑證，而不是一個 session 打天下

裝置、操作員、後台擁有者是三種完全不同的信任層級：裝置憑證在登入頁之前就得存在，用來認出這是哪個租戶的終端機；操作員 session 綁定當班身分做細粒度授權；Web session 是租戶擁有者忘記 PIN 時繞過操作員驗證的後路。一開始我把這三者混在一個 token 裡，結果任何一個場景的例外處理都會反過來污染另外兩個。拆開獨立驗證之後，加新路由時只要決定這個端點該認哪一種身分，不用擔心改壞既有的登入流程。

### 為什麼離線優先，而不是斷線就擋單

門市 Wi-Fi 不穩是常態，收銀不能因為訊號跳一下就卡住。我用 Dexie 把訂單先寫進 IndexedDB，outbox 佇列搭配指數退避＋隨機抖動輪詢同步，連線恢復後自動補送、監聽 `online` 事件。代價是任何跟送出訂單有關的功能，都要同時顧到離線佇列與線上直送兩條路徑。這是整個專案裡最容易漏掉、也最容易在上線後才發現的地方。

權限的分工也一樣明確：前端路由守衛只負責別讓使用者走進死路，實際的授權檢查一律在後端。

## 成果

七個功能模組全部完成並實際部署：前端在 GitHub Pages，後端 API 跑在 Cloudflare Workers，資料庫是 Cloudflare D1。CI 會在合併到 `master` 後自動套用資料庫遷移並部署前後端。
