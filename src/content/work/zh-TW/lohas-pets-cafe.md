## 這是什麼

樂活寵物咖啡廳是一個為寵物友善咖啡廳打造的九頁面品牌網站，用 Nuxt 4 靜態產生——每個頁面各司其職，從認識品牌、瀏覽菜單，到線上訂位，是一條完整走得通的路徑。

## 問題背景

形象網站常見的落差是「讓人想去」跟「讓人真的能去」中間的距離：圖片太大拖垮載入、內容藏在圖片裡搜尋引擎讀不到、網站沒講清楚怎麼去、幾點營業、訂不訂得到位子。

這個網站把這條路徑補齊——從瀏覽到訂位，每一步都有對應的頁面與明確的回饋。

## 我的做法

把敘事拆成九個各司其職的頁面：

- **`/reservation` 線上訂位。** 用 `vee-validate` + `zod` 做表單驗證，自動擋掉公休日與非營業時段的選項——使用者不會選到一個永遠不會被接受的時段。
- **`/contact` 完整的地址地圖與營業時間。**
- **`/menu` 用真實資料而不是圖片。** 價目表是結構化的 HTML 資料，不是烘進圖片裡的文字——搜尋引擎讀得到，也套得上 Menu 結構化資料。
- **圖片全面交給 `@nuxt/image`。** 自動輸出多尺寸 WebP，載入快、畫質不打折。
- **元件庫用 shadcn-vue。** 建立在 Reka UI 之上，元件原始碼直接收進 `app/components/ui`，不是黑盒依賴——要客製化行為或樣式時，改的是自己看得到、能完全掌控的程式碼。

## 技術決策與取捨

### 為什麼是多頁面而不是單頁

訂位表單、完整菜單、常見問題這類內容，使用者是帶著明確意圖去找的——單頁捲動找資訊，比不上有清楚網址、能直接分享或加書籤的獨立頁面。用 Nuxt 讓「多頁面」和「靜態產生」可以同時成立：`nuxi generate` 把每個路由都輸出成靜態檔案，部署方式簡單，架構上是完整的多頁應用。

### 為什麼選 shadcn-vue 而不是傳統元件庫

Element Plus 這類傳統元件庫把元件包成黑盒 npm 套件；shadcn-vue 的做法是把原始碼複製進專案裡。差別在於：訂位表單這種需要精準客製驗證邏輯與樣式的場景，直接擁有原始碼比繼承一個泛用元件的所有預設行為更省事。這是延續 MAJI POS 學到的判斷——工具要服務問題，而不是問題遷就工具的預設值。

### 深色模式要跟原生控制項同步

`@nuxtjs/color-mode` 切換的不只是 CSS class，也同步了 `color-scheme`，讓瀏覽器原生的表單控制項、捲軸這些不受 CSS 控制的 UI 一起換色，不會出現「網站是深色、輸入框卻是刺眼白色」這種不一致。

## 遇到的坑

**公休日的判斷要在客戶端和伺服器端一致。** 訂位表單一開始只在前端擋掉公休日的日期選項，但直接帶參數送出仍然會成功——後來把公休日規則抽成共用邏輯，前後端都跑同一份判斷，不能只靠 UI 擋。

**頁面轉場在非 Chromium 瀏覽器要有備案。** `experimental.viewTransition` 只有 Chromium 系瀏覽器支援原生轉場，其餘瀏覽器要確認退回的是「直接切換」而不是卡在轉場中間。

## 成果

九個頁面全部完成並可離線瀏覽（靜態產生），訂位表單會依當天日期即時擋掉不合法的選項，亮色與深色模式在所有頁面都完整支援。

## 如果重做我會怎麼改

1. **訂位表單接上真正的後端確認。** 目前送出後是寄信通知，還沒有「店家已確認」這個狀態能回饋給訂位的人。
2. **菜單價格交給簡單的內容管理。** 雖然已經不是烘在圖片裡，但改價格還是要改程式碼重新產生靜態頁面；一個輕量 headless CMS 能讓店家自己維護。
3. **加入更完整的社群分享圖。** 目前 OG 圖是單一張靜態圖，替不同頁面（菜單、訂位）產生對應的分享圖，分享出去時預覽會更準確。
